Ce fichier est le point d'entrée de toute session de développement assistée sur Cogenta.

## Règles de développement

## Avant d'écrire du code

Dans cet ordre, sans sauter d'étape :

1. `docs/00-vision.md` — si jamais lu.
2. `docs/03-decisions.md` — **une décision actée ne se rediscute pas.** Si elle semble
   mauvaise, le dire et attendre. Ne pas contourner.
3. `docs/lots/<lot en cours>.md` — périmètre, interfaces à produire, critères
   d'acceptation, pièges connus.
4. `docs/04-contrats.md` — uniquement les contrats que le lot consomme.

La commande `/lot <L0..L9>` fait ce chargement pour toi.

Quatre nouveaux codes `@cogenta/core` : `PLUGIN_SOURCE_NOT_FOUND`, `PLUGIN_MANIFEST_FILE_NOT_FOUND`, `PLUGIN_MANIFEST_LOAD_FAILED`, `PLUGIN_MANIFEST_EXPORT_INVALID`. **Tâche 3 faite** : worker isolé, protocole de messages (`packages/plugins/src/host/`, `packages/plugins/src/guest/sandbox-entry.mjs`) — la frontière de sécurité réelle du lot. Isolation à deux couches : un `worker_threads.Worker` (thread séparé, tué proprement, jamais l'hôte qui plante) spawné avec `env: {}` — les secrets et variables d'environnement de l'hôte ne sont jamais transmis, structurellement, pas par convention — et, à l'intérieur de ce worker, un contexte `node:vm` dont l'objet global ne contient ni `process`, ni `require`, ni `fetch`, ni aucun module natif : ils sont absents parce que jamais injectés, pas retirés après coup. Aucun callback `importModuleDynamically` n'est enregistré, donc `import()` dynamique est refusé nativement par V8 ; `codeGeneration: { strings: false }` bloque `eval`/`new Function`, fermant la technique d'évasion la plus courante (remonter la chaîne de prototypes jusqu'au vrai constructeur `Function`). `sandbox-entry.mjs` est écrit à la main en JS brut (pas compilé depuis TS) — même raison que les `cogenta.config.mjs` de l'installeur : ce fichier doit s'exécuter tel quel, chargé directement par `Worker`, sans étape de build. Protocole de messages sérialisés réel (`host/protocol.ts`) : `{id, type:'run', code}` → `{id, type:'result', value}` / `{id, type:'error', message}`, valeur toujours passée par un aller-retour JSON (aucun objet vivant ne traverse la frontière). `runIsolated`/`runIsolatedOrThrow` (`host/worker-runner.ts`) : un `Worker` neuf par appel (pas de pool — décision de la tâche 6, pas celle-ci), timeout hôte + timeout `vm` indépendant en second recours, `resourceLimits` réels sur le tas V8. Les quatre tests de sécurité exigés par le lot, réels et prouvés, pas simulés : tentative `import('node:fs')` refusée, requête réseau non déclarée refusée (`fetch` absent, pas seulement rejeté), accès à `process` refusé, secret du process hôte injecté dans `process.env` et prouvé inobservable depuis le worker. Boucle infinie testée et tuée sans affecter le process hôte. Surcoût de latence mesuré et documenté : **~46ms par appel isolé** (un `Worker` neuf par appel) contre un coût quasi nul en processus — mesure réelle, pas une estimation, capturée dans `test/host/worker-runner.test.ts`. Limitation honnête assumée dans le code et ici : `vm` seul n'est pas, de l'aveu même de la documentation Node, une frontière de sécurité durcie contre un attaquant colocalisé déterminé — la garantie réelle vient de la combinaison des trois couches (thread séparé + `vm` sans accès aux API Node + `env` vide), pas d'une seule d'entre elles. Trois nouveaux codes `@cogenta/core` : `PLUGIN_WORKER_TIMEOUT`, `PLUGIN_WORKER_CRASHED`, `PLUGIN_WORKER_RUNTIME_ERROR`. Ce que cette tâche ne construit pas, délibérément : le SDK réel côté plugin capacité-par-capacité (tâche 4/5) et la politique complète de limites de ressources/désactivation-avec-alerte (tâche 6) — seul le primitif d'isolation sur lequel ces tâches s'appuient. **Tâche 4 faite** : SDK côté plugin, construit dynamiquement selon les capacités accordées (`packages/plugins/src/host/capabilities.ts`, `packages/plugins/src/guest/sandbox-entry.mjs`) — jeu de départ délibérément minimal (« commencer minimal », mise en garde du lot elle-même) : `content.read`, `http.fetch:<domaine>`, `storage.read`/`storage.write:<préfixe>`, chacun un vrai handler côté hôte plutôt qu'une capacité de plus construite superficiellement. Protocole étendu (`host/protocol.ts`) pour un aller-retour RPC réel pendant l'exécution d'un run : le sandbox poste `{type:'sdk-call', callId, method, args}`, l'hôte exécute et répond `{type:'sdk-result'|'sdk-error', callId, ...}` — plusieurs appels SDK par run supportés, pas un aller-retour unique. La propriété « absente, pas seulement refusée » (critère d'acceptation explicite) est structurelle, pas conventionnelle : `sandbox-entry.mjs`'s `buildSdk(grantedCapabilities)` n'assigne une clé de méthode sur `sdk` que pour une capacité réellement présente dans la liste accordée — une capacité non accordée est une clé d'objet absente, jamais une méthode présente qui refuse à l'appel (`'content' in sdk` / `'read' in sdk.content` valent `false`, prouvé par test réel à travers le vrai worker isolé). Chaque handler re-vérifie la requête précise contre le paramètre précis accordé, jamais seulement « la capacité existe » : `http.fetch` re-checke le nom d'hôte réellement demandé contre l'ensemble des domaines accordés (un plugin autorisé pour `api.example.com` ne peut pas faire dériver son propre appel SDK vers `evil.example.com`) ; `storage.read`/`storage.write` re-checkent la clé demandée contre le(s) préfixe(s) accordé(s), avec refus explicite de tout segment `.`/`..` (fermeture de la traversée de chemin). Testé de bout en bout à travers le vrai worker isolé (pas seulement les handlers hôte en isolation) pour au moins une capacité : le sandbox appelle réellement `sdk.content.read(...)`, le message traverse le protocole, l'hôte lit un vrai `ContentStore` (SQLite réel), le résultat revient dans le sandbox. Un nouveau code `@cogenta/core` : `PLUGIN_CAPABILITY_REFUSED`. **Tâche 5 faite** : traduction capacités → objet SDK, avec absence des méthodes non accordées (`packages/plugins/src/permissions/`) — la couche de données qui manquait à la tâche 4, où `buildSdk` acceptait `grantedCapabilities` comme un paramètre externe déjà décidé. `PluginGrantStore` (`grants.ts`, table `cogenta_plugin_grants`, patron `ensureChannelTables`/`ensureAuthTables` repris à l'identique — pas de fichier de migration séparé) persiste une concession par `(pluginName, chaîne de capacité exacte)` : `http.fetch:api.exemple.com` accordé ne couvre jamais implicitement `http.fetch:evil.com`, même nom nu partagé. `resolveGrantedCapabilities(manifest, grants)` (`resolve.ts`) est la vraie traduction que le titre de la tâche nomme : l'intersection entre ce que le manifeste courant déclare et ce qui a réellement été approuvé — une concession périmée pour une capacité que le manifeste ne déclare plus ne fuite jamais, une capacité déclarée-mais-jamais-accordée n'est jamais incluse. La garde « une nouvelle version ne s'installe jamais automatiquement avec plus de permissions » (piège nommé du lot) découle de cette intersection par construction, pas d'un second mécanisme : une capacité nouvellement déclarée n'a encore aucune ligne de concession, donc elle reste absente de la liste résolue — et donc du SDK (propriété « absente, pas refusée » de la tâche 4) — tant que personne n'appelle `grant()` pour elle. `detectCapabilitiesNeedingApproval` rend cet ensemble « nécessite une nouvelle approbation » explicite et testable pour l'écran de permissions (tâche 7, pas encore construit). `runPlugin(manifest, code, grants, options)`, nouveau vrai point d'entrée dans `worker-runner.ts`, calcule lui-même `grantedCapabilities` via `resolveGrantedCapabilities` plutôt que d'accepter une liste externe — ferme le point d'entrée que la tâche 4 avait laissé ouvert, prouvé de bout en bout à travers le vrai worker isolé (y compris le scénario de mise à jour : un manifeste déclarant une capacité neuve, exécuté contre d'anciennes concessions, ne l'expose jamais). **Tâche 6 faite** : limites de temps, de mémoire, arrêt et désactivation (`packages/plugins/src/host/worker-runner.ts`, `packages/plugins/src/permissions/disabled.ts`) — la tâche 3 posait déjà un timeout minimal et de vrais `resourceLimits` sur le tas V8 ; cette tâche construit la vraie politique complète par-dessus. `IsolatedRunResult.reason` (`'timeout'|'memory'|'crash'`) classe chaque échec : `'timeout'` vient du kill switch existant, `'memory'` est détecté par un filtre réel sur le message d'erreur que Node pose sur l'événement `'error'` du `Worker` quand `resourceLimits` est dépassé (observé : « Worker terminated due to reaching memory limit: JS heap out of memory » — Node ne fournit pas d'événement dédié, seulement ce message, donc la classification est un filtre de motif volontairement étroit, pas une supposition sur une API documentée), tout le reste tombe dans `'crash'`. Seuls `'timeout'` et `'memory'` désactivent le plugin — une erreur JS ordinaire ne le fait jamais, lecture littérale de « dépasse son temps ou sa mémoire ». Désactivation réelle et persistée : `PluginDisableStore` (`disabled.ts`, table `cogenta_plugin_disabled`, même patron `create table if not exists` que `cogenta_plugin_grants`) — `runPlugin` exige désormais un `disableStore` et refuse (`PLUGIN_DISABLED`, nouveau code) de même spawn un worker pour un plugin déjà désactivé, vérifié avant chaque run, pas seulement après une violation. Le volet « avec alerte » est un callback structurel (`onPluginDisabled?`), jamais une dépendance dure vers `@cogenta/channels` ou un transport précis — câbler une désactivation à une vraie notification est une décision d'intégration pour qui assemble un site, pas le travail de ce paquet (même patron que `AuditLogLike`/`ContentServiceLike` ailleurs dans ce dépôt). Prouvé par des tests réels à travers le vrai worker isolé : une fixture d'épuisement mémoire réelle (allocation non bornée) déclenche effectivement le plafond `resourceLimits` et est classée `'memory'` ; le process hôte survit et reste utilisable après chaque type de violation (un run indépendant immédiatement après réussit) ; un plugin désactivé est refusé au prochain run avant même qu'un worker soit créé ; un humain peut réactiver un plugin désactivé (`enable()`). Un nouveau code `@cogenta/core` : `PLUGIN_DISABLED`. **Tâche 7 faite** : écran de permissions en langage clair (`packages/plugins/src/permissions/describe.ts`, `packages/admin/src/plugins/permission-review.tsx`) — `describeCapability` traduit chacune des vingt capacités du vocabulaire figé (`PLUGIN_CAPABILITY_NAMES`, tâche 1) en une vraie phrase française plus un niveau de risque (`low`/`medium`/`high`) et une catégorie, jamais un identifiant technique brut ; les deux exemples littéraux du lot sont reproduits exactement (`http.fetch:api.exemple.com` → « Ce plugin pourra envoyer des données à api.exemple.com », `content.write_draft` → « Ce plugin pourra créer et modifier des brouillons, mais pas publier »). Une capacité hors vocabulaire lève une erreur plutôt que de tomber sur une phrase générique — un repli générique aurait justement été le genre de non-réponse proche de l'identifiant brut que le critère d'acceptation interdit. Risque `high` pour les capacités destructrices ou qui contournent la validation humaine (`content.publish`, `content.delete`, `site.config_write`, `deploy.trigger`, `agent.delegate`, `memory.write`), jugement réel par capacité, pas une formule. Propriété « aucun identifiant technique brut » vérifiée mécaniquement sur tout le vocabulaire réel (pas seulement les deux exemples du lot) par un test qui cherche des fragments bruts (`content.`, `http.fetch:`, `_draft`, etc.) dans chaque phrase produite. Écran réel côté admin : `PluginPermissionReview`, purement présentationnel et piloté par props (aucune dépendance dure vers `@cogenta/plugins` — types locaux structurels, même patron que `content-client.ts`'s `ContentBlock` déjà établi dans cette appli), puisqu'aucun flux d'installation de plugin n'existe encore nulle part dans ce dépôt (aucun registre de plugins vivant). Liste à cocher par élément comme chemin par défaut ; « tout autoriser sans lire » existe mais reste une action secondaire, jamais le bouton principal — « l'installation sans lecture est possible, mais on ne la facilite pas ». Un élément à risque élevé coché exige une confirmation supplémentaire explicite avant de pouvoir être approuvé. La révocation (tâche 8, « révisables après installation, et révocables ») a déjà sa couche de données réelle depuis la tâche 5 (`PluginGrantStore.revoke`) — cet écran de traduction est conçu pour être réutilisé tel quel par le futur écran de révision, pas reconstruit. **Tâche 8 faite** : révision et révocation de permissions après installation (`packages/plugins/src/permissions/review.ts`, `packages/admin/src/plugins/granted-permissions.tsx`) — une tâche d'assemblage, pas de nouveaux primitifs : `listGrantedCapabilities`/`revokeCapability`/`describePendingApproval` composent uniquement des pièces déjà réelles (`PluginGrantStore` et `resolveGrantedCapabilities`/`detectCapabilitiesNeedingApproval` de la tâche 5, `describeCapability` de la tâche 7) — aucune nouvelle table, aucune nouvelle traduction. `revokeCapability` prouve la propriété de bout en bout qui compte réellement : après révocation, `resolveGrantedCapabilities` exclut vraiment la capacité — la méthode SDK redevient absente (propriété « absente, pas refusée » de la tâche 4), pas seulement « marquée révoquée » dans une table pendant que le SDK continue de l'exposer. Écran admin `PluginGrantedPermissions` : le pendant post-installation de `PluginPermissionReview` (tâche 7) — liste des concessions actives avec une vraie action de révocation par élément, plus une section « nouvelles autorisations demandées » clairement séparée (réutilise `PluginPermissionReview` tel quel, pas une deuxième interface de revue) quand une mise à jour de plugin déclare une capacité au-delà de ce qui est déjà accordé. Aucun écran de liste de plugins vivant n'existe encore nulle part dans ce dépôt (tâches 12-13) — ce composant est réel et testé, prêt à être monté par cet écran une fois qu'il existera, pas une navigation bout-en-bout construite vers nulle part. **Tâche 9 faite** : signature et vérification (`packages/plugins/src/signing/`) — Ed25519 réel via `node:crypto` (zéro dépendance, R9), pas le HMAC symétrique déjà utilisé par L6 (canal/approbation) : un registre signe une fois, chaque installation Cogenta doit pouvoir vérifier sans jamais détenir le secret de signature, ce qu'un schéma à secret partagé ne permet pas. `signManifest`/`verifyManifestSignature` signent une canonicalisation déterministe (clés triées) du manifeste entier — pas seulement son nom, une signature qui ne couvrirait que le nom prouverait la paternité d'une étiquette, pas de ce que le plugin déclare faire ; volontairement borné au manifeste, pas au code réel du plugin, puisqu'aucun mécanisme ne lit encore le code d'entrée d'un plugin dans une chaîne (`loadPlugin`, tâche 2, ne fait qu'importer le module de manifeste). `TRUSTED_REGISTRY_PUBLIC_KEYS` démarre vide — aucun registre réel n'existe encore (pre-alpha), donc tout plugin `registry` échoue la vérification par défaut plutôt que de faire confiance à une clé factice. La signature voyage en fichier sibling (`<manifeste>.sig`), jamais un champ du manifeste lui-même — signer ne change jamais la forme de `PluginManifest`. `resolveSignatureStatus`, appelée par `loadPlugin` pour toute résolution : un plugin `registry` sans signature ou à la signature invalide est refusé avant même l'import du module de manifeste (`PLUGIN_SIGNATURE_MISSING`/`PLUGIN_SIGNATURE_INVALID`) — aucun paramètre nulle part ne permet de forcer le passage, l'absence même de cette échappatoire est la façon dont « sans possibilité de passer outre depuis l'interface » est tenu. Un plugin `local`/`git` reste autorisé sans signature (« mode développement »), et `ResolvedPlugin` porte désormais `devMode`/`signatureVerified` réels pour qu'un futur bandeau admin rende l'« avertissement permanent » du lot. Deux nouveaux codes `@cogenta/core` : `PLUGIN_SIGNATURE_MISSING`, `PLUGIN_SIGNATURE_INVALID`. **Tâche 10 faite** : galerie de skins avec validation automatique (`packages/plugins/src/registries/skins.ts`) — le premier des quatre registres nommés par le lot (« Registres » : plugins/thèmes/skills/skins), et le seul dont la porte est purement automatique (« sans revue humaine ») puisqu'un skin est un JSON de tokens qui n'exécute jamais de code, contrairement aux trois autres registres qui exigent tous une revue et/ou une signature. `createSkinGallery.submit` réutilise `validateSkin` de `@cogenta/render` telle quelle (tâche déjà bâtie en L9 tâche 7, jamais réimplémentée) : succès → `accepted`, échec → `rejected` avec le code d'erreur réel et précis de `validateSkin` capturé (`SKIN_CONTRAST_INSUFFICIENT`, `SKIN_SCALE_NOT_MONOTONIC`, etc.), jamais un « invalide » générique — aucun état « en attente » n'existe dans la table, la décision est prise une seule fois, à la soumission. Persistance `cogenta_skin_gallery` (même patron `create table if not exists` que les tables de `permissions/`/`signing/`). Corpus de test repris du même esprit que celui de la tâche 7 du L9 (candidats valides + un par catégorie d'échec réelle de `validateSkin`), taux de rejet mesuré et assert. `@cogenta/plugins` gagne une dépendance réelle vers `@cogenta/render`. Une abstraction `Registry<T>` partagée pour les tâches 11-13 n'a pas été construite maintenant — un seul registre concret existe encore, sous le seuil des trois usages réels d'AGENTS.md ; à réévaluer une fois skills/thèmes/plugins construits. **Tâche 11 faite** : registre de skills (`packages/plugins/src/registries/skills.ts`) — le deuxième des quatre registres, et le premier dont la porte diffère réellement de celle des skins : le tableau « Registres » du lot exige « Revue de contenu » pour les skills, pas une validation purement automatique. Réutilise `parseSkillFile` de `@cogenta/agents` (nouvelle dépendance workspace de `@cogenta/plugins`) comme pré-contrôle automatique nécessaire mais non suffisant : une soumission qui ne se parse même pas comme un fichier de skill valide est refusée immédiatement, avec la vraie erreur de parsing, et n'atteint jamais l'état `pending` — mais une soumission qui se parse correctement reste `pending`, en attente d'une vraie décision humaine (`review(id, 'accept'|'reject', reviewerUserId, notes?)`), contrairement à la galerie de skins où la validation automatique suffit seule. Rejouer une décision déjà prise renvoie un résultat discriminé (`{ok:false, reason:'already_decided', entry}` portant la décision antérieure) plutôt qu'une erreur brute ou une réécriture silencieuse ; une soumission auto-rejetée (jamais `pending`) ne peut jamais être revue. Persistance étendue dans `ensureRegistryTables` (même fonction que la tâche 10, patron `create table if not exists` inchangé — une seule fonction possède désormais les deux tables de registre). Abstraction `Registry<T>` partagée toujours pas construite : les deux machines à états sont réellement différentes en forme (skins : un seul verdict automatique ; skills : pré-contrôle automatique puis décision humaine séparée), les forcer dans un type générique commun coûterait plus de clarté que la petite duplication de forme submit/list/get n'en économise — à réévaluer une fois les registres thèmes/plugins (tâches 12-13) construits. **Tâche 12 faite** : registre de thèmes (`packages/plugins/src/registries/themes.ts`) — le troisième des quatre registres, et le premier avec deux portes réelles au lieu d'une : le tableau « Registres » du lot exige « Signature, contrat vérifié » pour les thèmes, contre une seule condition pour skins (validation automatique) ou skills (revue de contenu). **Signature** : le primitif Ed25519 de la tâche 9 (`packages/plugins/src/signing/`), généralisé de `PluginManifest` uniquement vers tout contenu canonicalisable (`canonicalizeContent`/`signContent`/`verifyContentAgainstTrustedKeys`, les fonctions spécifiques au manifeste devenant de simples enveloppes) — un manifeste de thème est signé et vérifié avec exactement la même machinerie, aucun second schéma de signature inventé. ## Mode de travail : autonomie

Décider, coder, livrer, puis rendre compte. Ne pas demander la permission pour une
décision de conception : la prendre, la tracer, et la signaler dans le rapport.

**S'arrêter pour demander uniquement dans trois cas :**

1. Une action **irréversible vers l'extérieur** — publier sur npm, supprimer des
   données, déployer en production.
2. Un **secret ou un accès** que seul l'humain détient.
3. Un choix qui **contredirait une décision déjà actée** dans `docs/03-decisions.md`.

Tout le reste s'avance. Une décision discutable signalée dans un rapport coûte une
correction ; une question posée coûte une journée d'attente.

## Gouvernance documentaire

`docs/03-decisions.md` est **append-only** : une décision actée ne se modifie pas. Pour
changer d'avis, écrire une **nouvelle** ADR et marquer l'ancienne
`Remplacée par ADR-XXXX`, sans supprimer son texte.

`docs/04-contrats.md` est versionné en semver. **A (`schema@1.0`) et B (`blocks@1.0`)
sont figés** depuis le 2026-08-13 : les modifier impose une montée de version majeure et
une note de migration du contenu déjà saisi. C et D ne sont pas encore figés.

Ces règles s'appliquent par discipline, plus par un hook.

## Rappels qui coûtent cher quand on les oublie

- **Pas de `any`, pas de `@ts-ignore`, pas de CommonJS.** ESM uniquement.
- **Jamais `throw new Error("…")` nu** dans du code de bibliothèque : `CogentaError`
  avec `code` stable et `hint`.
- **Jamais `console.log`** : logger structuré.
- **Pas de mock de la base.** Base réelle éphémère.
- **Le driver dégradé est testé**, pas seulement l'optimal.
- **Un `TODO` sans issue GitHub associée est interdit.**
- Commits en Conventional Commits, avec `Signed-off-by`. Code, commentaires, commits
  et issues **en anglais** ; les documents de conception sont en français.
